# M4 验收记录

日期：2026-10-03。规则 `facility-zero/1`，规范编码 `core-state/1`，传输 `observer/1`、`replay/1`，运行摘要 `run/1`。环境：Windows、全局 .NET SDK 10.0.401、Release、零第三方 NuGet 依赖、Python 3。

结论：M4 的投影、订阅、权威记录、回放与动作核验已在本机通过验收（T401–T406）。跨平台、进程树清理与终端渲染仍未验证，属 M6/M5。

## 已交付

- **独立投影与 reducer**：`ObserverProjection` 从 Core 快照计算 `ObserverPatch`；`VisualState` 独立重建显示状态。补丁显式包含 `tile_upserts`、`entity_upserts`、`entity_removals`、`visible_tiles`、`inventory`、`mission_phase`、`episode`，清空值以 `null` 显式输出而不是省略。
- **订阅 Hub**：注册与发布共用同一把锁，`Register()` 原子返回 `(snapshot, subscription)`，快照的 `BaseSeq` 是其后第一条增量的前置序号；每个订阅者有独立有界队列（容量 1–1024，默认 128；同一 Hub 最多 32 个订阅），队满即摘除并置 `RequiresResync`，不使用 DropOldest 继续应用错误状态。
- **权威记录器**：`RunCommitter` 是唯一发布者，顺序固定为 Core 计算 → 权威 append 成功 → 发布；append/flush 失败立即闩锁（`_broken`），该步不发布、不再写 footer，摘要改用最后已提交快照。
- **回放**：`ReplayReader` 以固定缓冲流式读取，限制单条记录大小；缺 footer / 末行残缺标 `incomplete` 并可播放完整前缀，中间损坏停止并给出行号。`ReplayService.Export` 不构造 Core；`Verify` 用同版 Core 重演动作并逐步比对哈希、反馈、事件与补丁，首个不一致步返回其记录行号与 tick。
- **CLI 命令面**：`run --record`、`run --observer-stdout`、`replay`、`verify`；`--observer-stdout` 独占 stdout 并把摘要送到 stderr；`--headless` 表示不挂终端旁观者，与 `--observer-stdout` 互斥（冲突返回 2）。

## 本机实际执行与结果

```powershell
dotnet build AgentGame.slnx -c Release
dotnet run --project tests/AgentGame.Core.Tests -c Release --no-build
dotnet run --project tests/AgentGame.Protocol.Tests -c Release --no-build
dotnet run --project tests/AgentGame.Runtime.Tests -c Release --no-build
dotnet run --project tests/AgentGame.Architecture.Tests -c Release --no-build
```

构建 0 警告、0 错误。四个验收程序共 **203 项**全部通过：

| 程序 | 项数 | 明细 |
|---|---:|---|
| Core | 39 | 规则、视野、快照独立性、规范哈希 |
| Protocol | 44 | 22 项基础契约 + 22 项 M4 编解码（Observe/Replay 严格校验） |
| Runtime | 108 | 10 场景服务 + 36 M3 会话/进程 + 9 Observer + 29 Replay + 7 Hub + 9 集成 + 8 CLI 黑盒 |
| Architecture | 12 | 项目引用与禁止依赖、SDK/编译约束 |

M4 CLI 黑盒检查（8 项，全部真实启动 `dotnet agent-game.dll` 子进程）覆盖：`generate → validate → run --record → replay → verify` 全链路；篡改 action 与篡改 `core_hash` 均在**首个不一致步**被指出（记录行号与 tick）；删除 footer 后 replay 仍导出完整前缀但状态为 `incomplete`、verify 明确不报告一致；中间行损坏时停止并给出行号；`--headless` stdout 恰好一行 `run/1` JSON；记录路径不可写时报 `record_error` 且不发布任何步；**故意不读 stdout 管道**导致观察者端背压时，固定动作的最终 tick、结果种类与逐步哈希与无订阅者时完全一致；`--headless` 与 `--observer-stdout` 冲突按用法错误拒绝。

`replay` 导出的是**全部**已提交 envelope：初始 snapshot、每个回合一条 `agent_status`（waiting）与一条 `step_batch`、以及结束时的一条收尾 `agent_status`（stopped/errored），共 `2N+2` 条；记录文件本身另含 header 与 footer，所以 `lines` 为 `2N+3`。测试按 envelope 类型计数而不是按总行数。

## 独立审计与处理

一个独立只读子代理对 M4 做了对抗性审查，提出 4 条；主代理逐条复核：

| 结论 | 内容 | 处理 |
|---|---|---|
| 成立 | 退出码与 `project-plan.md` 早期建议（3/4/5）不符，且与 `runtime-execution.md` 的既有约定互相冲突 | 采用已冻结的实际约定（0/1/2/130），把计划中的建议改为“已由 M3 决策取代”，并说明机器可读契约是 JSON 的 `error.code`/`valid`/`line`；新增黑盒检查固化 `--headless` 冲突返回 2 |
| 成立 | `--headless` 被解析但无任何语义 | 赋予语义（不挂终端旁观者、与流式互斥），帮助文本与计划同步更新 |
| 不成立 | “记录失败后仍把未提交的成功终局发给 Agent” | `RunCommitter.StepAsync` 抛出的是 `RecordingException`，在 `GameRunner` 第 71 行被捕获并置 `kind=execution_error`，第 56–58 行的成功分支不可达；集成检查另有 “Failure recording the second step preserves only the first committed action” 覆盖摘要只反映最后已提交状态 |
| 不成立 | “≥64 KiB+1 的场景文件被静默截断后用另一张地图开局” | `ScenarioService.Read` 最多读 `MaxLineBytes+1 = 65537` 字节，而 `ScenarioCodec.Parse` 对 `> 65536` 必然抛错，因此超限文件一定被拒绝；已有“Bounded reads reject oversized files”检查覆盖 65537 字节输入 |

审计同时记录一条未验证疑虑：`ConsoleObserverSink` 在取消与 `RequiresResync` 置位之间存在窄竞态，理论上可能不报 `resync_required`。当前仅在取消/结束路径上出现，未构造出稳定复现，保留为已知风险而不是已修复项。
