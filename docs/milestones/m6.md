### golden 与确定性（T601 的 Windows 部分）

1. 同一固定局跑两次 → 两次摘要的 `core_hash` 逐字节一致，且等于冻结向量 `a68fe87640e7105142f481a59e77f43bdb854bab61a826e38ae4fd77ae323262`。
2. `scenario validate` 的 `initial_hash` 等于冻结 `932e1d591f8e19764177838757f3117c8dbcd19e202e47f806ff4bb50c49d286`；运行再现冻结成功哈希；`verify` 报 `valid=true` 且哈希一致。
3. `verify` 两次 stdout 逐字节一致；两次执行后记录文件字节与长度完全不变（核验是纯只读投影）。
4. `--headless` 与 `--observer-stdout` 跑同一固定局，`kind`/`tick`/`core_hash` 完全相同（挂观察者不改变规则结果）。

### 进程树清理（T602 的 Windows 部分）

1. 决策超时（`--decision-ms 1500`）时：宿主退出码 1、`error.code=decision_timeout`、`tick=0`，且夹具进程与其**孙子进程**都不再存在；pidfile 里的 `parent` 与摘要的 `agent_process_id` 一致（证明夹具真的运行过）。
2. 夹具拒绝正常关闭（`episode_end` 后 sleep 60）时：宿主退出码 0、`kind=turn_limit`、`tick=13`、`forced_termination=true`，父子 PID 同样全部消失。
3. 夹具自身有效性：不经宿主单独启动，2 秒后确认孙进程仍在运行，随后 `Kill(entireProcessTree: true)` 使两者消失——该检查保证前两项不是"夹具没跑起来"的假通过。

### 1000 种子扫描（T603 的生成部分）

seed 0–999、`maxTicks 512 / maxReferenceLength 128 / maxAttempts 16`：

- **成功 1000/1000，失败 0**；生成尝试分布 **1 → 1000**（全部一次成功）。
- 最大 `reference_length` **101**（上限 128）；墙钟 **1.952 秒**（主代理重跑结果一致）。
- 证据：`artifacts/m6-seed-sweep/report.json`（含 successes/failures/seedFailures/attemptsDistribution/maxReferenceLength/机器与 SDK）。

### 资源上界与分层性能（T603 的本机部分）

`M6ResourceChecks`（4 项）与 `artifacts/m6-perf/report.json`：

- **有界慢订阅者**：容量 1 且完全不消费的订阅者，在 64 回合的局里仍得到 `kind=turn_limit`、`tick=64`，订阅者被置 `RequiresResync` 并脱离，排空后只剩 **1** 个信封——队列有界且规则结果不受影响。
- **记录线性、不重复**：N=64 → `step_records=64`（等于已提交 tick）、`total_lines=131`（等于 `2N+3`）、59882 字节、**935.7 字节/步**（上限 8192）。
- **重复 5 次无累积**：同一短局重复运行，hub 快照与记录行数每次完全一致。
- **分层计时**（本机 Windows NT 10.0.26300 / .NET 10.0.12）：100 次 `Generate+Validate` **0.149 s**；200 次 `Step+Capture+Observe` **52 µs**（在 9×3 的 `facility-small` 上，约 0.26 µs/步）；1000 次 `StateEncoding.Hash` **431 µs**；`ReplayService.Verify`（64 步记录）**3 ms**；一次完整 CLI 子进程 + Python Agent 的一局 **0.693 s**。
- **主代理修复的度量缺陷**：原实现把亚毫秒计时四舍五入到毫秒，导致报告里 `core_steps`/`hash` 记为 **0**，这样的数字无法用于回归对比。现改为同时记录秒（6 位小数）与**微秒**，并把误导性的 `*_total` 字段名改为带单位的 `*_seconds`/`*_micros`。
- 注意：Core 步进计时是在 9×3 手工样例上测的，不代表默认 21×13 地图；这些上限是"宽松回归护栏"，不是吞吐承诺。

## 已知限制

- **仅 Windows**：Linux 构建与 `setsid` 分离进程的清理未验证；`Kill(entireProcessTree: true)` 依赖 Windows 的作业对象机制，不能推断 Linux 行为。Linux 部分明确保留为发布门槛。
- **PID 复用**：进程树检查以 PID 消失为判据。若在 10 秒等待窗口内发生 PID 复用，检查会**失败**（假阴性）而不是假通过；该风险方向安全，但可能带来偶发 flake。
- **未做的 M6 项目**：发布包与依赖锁定、快速上手与故障示例、`scripts/*.ps1`（pwsh 7）黑盒脚本重跑（本会话只有 Windows PowerShell 5.1，脚本用到 `ProcessStartInfo.ArgumentList` 与 `Kill(entireProcessTree)`，需 pwsh 7 才能跑完整链路）。
- Core 步进/哈希的计时只在 9×3 样例与单机负载下测得；跨机器比较意义有限。
- 终端画面仍未在真实交互终端里肉眼确认（M5 遗留项）。
