# 多玩家游戏需求研究（新阶段提案）

状态：**M7.1–M7.3 的 Core、协议、每视图 Observer 与双席位 Runtime 已实现并验收**（见 [milestones/m7.md](milestones/m7.md)）；CLI 会话清单及终端接入待 M7.4。日期：2026-10-04。本文回答一个新阶段需求：**多玩家游戏——每个玩家可以选择接入游戏，无论他是人类玩家还是另一个不同的 Agent**。

依据：冻结报告 [agent_game_research_2026-10-02.md](../agent_game_research_2026-10-02.md) 第 15.8 节（OpenSpiel/PettingZoo 的 State/Observation 分离、AEC 顺序行动与 Parallel 同时行动、API 合规测试）、第 7 节（单一逻辑属主、外部调度多局面）、第 9/10 节（超时与 Observer 信息边界），以及 [项目实施计划](project-plan.md) 第 2 节把"多 Agent"放在"后续按需"桶、并要求"范围变化必须写明对规则、协议、记录与验收的影响"。

报告的硬判据（直接决定本轮研究口径）：

> 首版不预建玩家调度、同时动作合并和可变 Agent 集合。**给几个字段加 agent_id 不是已经支持多 Agent**，顺序、信息隔离和终止语义都需要重新设计。

因此本文不从"给协议加个 player 字段"出发，而是先定**行动顺序、信息隔离、终止语义**三件事，再谈协议与运行时。

## 0. 已确认的范围决策（2026-10-04）

| 问题 | 决定 |
|---|---|
| 接入范围 | **仅本地多席位**：同机 2 个席位，可以是人类或进程 Agent；席位身份不绑定进程/socket，网络接入将来只换传输层 |
| 目标形态 | **首版协作**：门卡与门共享（任一持卡席位可开门）；**核心由拾取它的那一个席位携带**，该携带者必须自己走到出口才算成功。**未来允许互相干扰/敌对**，作为独立规则版本引入，而不是协议重写（见 D12） |
| 连接生命周期 | **固定席位**：运行开始时配满；中途不加入、不重连；退出/断开后该席位此后自动提交 `wait` 并照常记录 |
| 席位规模 | **首切片恰好 2 席**；3–4 席是后续参数扩展，但每视图补丁扇出与记录体积需先量测 |

## 1. 目标与非目标

### 目标（本阶段要解决的问题）

1. 一局内可以有多个玩家席位（seat），每个席位独立决策。
2. 席位可以是**人类**（本地交互输入）或**任意 Agent**（外部进程），两者在同一条规则与提交路径下等价。
3. 每个席位只看到**自己**的局部信息；旁观者另有视图，且旁观数据绝不回流给 Agent。
4. 保持项目既有承诺：单一逻辑属主、权威先记录后发布、可复现的规范哈希、离线 `replay`/`verify`、订阅者有界队列与 `base_seq` 连续。
5. 人类与 Agent 混排的一局可以记录、回放并核验。

### 首切片非目标（明确不做，避免范围爆炸）

- 网络传输与远程接入（先做本地；但设计不得把"席位身份"绑死到进程或 socket）。
- 中途加入、断线重连、bot↔human 中途置换、可变席位集合。
- 每玩家独立门卡/门、per-seat 视野半径、对抗/竞速积分、动态危险。
- 同时提交（Parallel）与冲突仲裁——留到明确需要时再评估。
- 并发多局面调度（报告第 7 节的"外部调度多局面"是评测层的事，不在本阶段）。

## 2. 关键设计决策（附推荐默认）

| # | 决策 | 推荐默认 | 理由 |
|---|---|---|---|
| D1 | 行动顺序 | **严格座次轮转**（AEC 式顺序行动）：每轮按 seat 0..N-1 各推进一步，一步 = 一 tick | 与现有"一动作一回合、Core 串行、同步 Step"完全同构；无需新冲突规则；哈希与记录契约不变。同时提交会引入"同格冲突如何定序"，且必须固定解冲突顺序才能保持 `verify`，复杂度高 |
| D2 | 同一格多人 | **允许叠加**，玩家之间不阻挡（首切片） | 避免引入碰撞规则与其对可解性的影响；后续若需要推挤，作为规则版本变更单独讨论 |
| D3 | 门卡/门/核心 | **门卡与门共享**：任一席位拾取即全队持有，任一持卡席位可开门。**核心是单一携带者**：拾取它的席位持有它，不能被第二个席位拾取，也不能转移；只有携带者本人到达出口才算成功 | 若把核心也做成"全队共享"，成功判定会退化成"队伍有核心 且 任一席位在出口"——2 席时一人先站到出口、另一人独自取核心即可立刻获胜，**返程要求被绕过**（该漏洞在 M7.1 审查中被发现并修正）。共享门卡与门则无害：开门不需要特定的"人"把门搬回去 |
| D4 | 胜负 | **协作**：核心携带者到达出口 → 全员成功；回合上限共享 | 保留 key→door→core→exit 的拓扑意义（报告第 8 节：拓扑才保证可解）；携带者规则保证"取核心并返回"这一步真实发生 |
| D5 | 超时 | 未在决策期限内响应的席位，其该回合动作按 **已提交的 `wait`** 记录，游戏继续 | 与 M3 既有"非 legal 响应不推进 Core、超时不伪造动作"一致；关键是超时结果必须**真正进入权威记录**，否则 `verify` 对不上 |
| D6 | 席位来源 | 本地：进程 Agent 或进程内人类；**席位是 Core 内的序号**，不绑定进程/socket | 网络接入将来只是把同一套规范动作搬到 socket，不重写协议 |
| D7 | 连接生命周期（首切片） | 运行开始时配置全部席位；主动退出/断开后该席位此后自动 `wait`（照常记录）；不做中途加入与重连 | 报告明确"可变 Agent 集合"需要重新设计终止语义，先不碰 |
| D8 | 信息隔离 | `view=agent:<seat>` 只投影该席位的可见信息；`view=spectator` 可看公开全图，但绝不下发给任何 Agent | 报告第 10 节与 M4 已冻结的"全图视图必须显式指定且与 Agent 隔离" |
| D9 | 协议演进 | 一次性冻结 seat 化的新一套：`agent/2`、`observer/2`、`replay/2`、`scenario/2`；`core-state/2` 覆盖所有席位 | 避免"四处分别加字段"造成的版本矩阵错配（同一档案的 Agent/Observer/回放版本必须成套） |
| D10 | 旧档案 | 保留 `facility-zero/1` + `core-state/1` 的只读核验路径，旧记录仍可 `verify` | 现有 `ReplayService.Verify` 严格比对 `RulesVersion`；若直接替换规则版本，已发布的单机档案会永远无法核验 |
| D11 | 席位配置方式 | 新增会话清单文件（如 `--session seats.json`）描述席位种类与命令 | N 个异构席位的命令行标志会迅速失控；清单也让"人类/Agent/只等待"可声明 |
| D12 | 敌对/干扰的缝 | `Scenario` 增加 `mode` 字段：首版 `coop`；将来 `adversarial`。玩家互相阻挡、抢夺、独立目标等**只改规则版本与 `mode`，不改协议形状** | 用户明确"未来也可以互相干扰/敌对"。若把"允许叠加/共享对象"写死在协议里，将来做敌对就是协议重写 |
| D13 | 玩家间碰撞 | 首版协作允许同格叠加（无碰撞）；若将来做敌对，碰撞/阻挡作为 `adversarial` 规则版本的显式规则加入，并同步进入 `core-state` 哈希与验收 | 碰撞会改变可解性判定与哈希覆盖，必须版本化而不是静默改变行为 |

## 3. 必须存续的不变量
这些是现有实现的承诺，多玩家化**不得**破坏（破坏即视为设计失败）：

1. 一局只有一个逻辑属主调用 Core；异步只存在于外围（stderr 排空、订阅消费、记录写入）。
2. 权威记录成功先于发布；记录/flush 失败时不发布该步、不继续运行、摘要按最后提交状态报告。
3. Core 不含墙钟、随机、I/O：**回合顺序必须由座次与 tick 决定，不能由到达时间决定**，否则跨进程哈希不可复现。
4. 规范状态哈希覆盖全部影响规则的多人状态（每个席位的位置、共享库存/门状态、tick、终局）。
5. 每个订阅者独立有界队列，`base_seq + 1` 连续；慢订阅者脱离而不是应用错误状态。
6. `replay` 不需要 Core/Agent 即可播放；`verify` 用同版规则重演规范动作并逐步比对。

## 4. 影响面（按模块，含具体触点）

以下为对现有代码的实际触点（由只读影响分析给出并经主代理复核）：

**Core（必须扩最多）**
- `Game.Step`（`src/AgentGame.Core/Game.cs`）目前是"每 tick 单一动作、单一玩家状态"；需要按席位的推进入口与轮转。
- `Game.Capture/Observe`：单坐标单库存 → 每席位位置与共享/每席位库存的选择（按 D3 为共享）。
- `StateEncoding`：`core-state/1` 只编码一个 `Position` 与三项布尔；需 `core-state/2` 逐席位序列化，否则哈希无法证明多人状态。
- `Scenario`：单一 `start` → 每席位出生点；出口/门卡/门/核心仍单一（D3）。

**Protocol**
- `AgentMessages`、`ObserverMessages`、`ReplayRecords` 都缺席位标识；`ObserverCodec`/`AgentResponseParser` 固锁 `protocol` 与 `view=="agent"`，需支持 `agent:<seat>`/`spectator` 与 seat 字段。
- 回放记录需要"该步属于哪个席位"，否则重演无法还原轮转。

**Runtime**
- `GameRunner`/`HumanSession` 的单 `while` + 单 decide + 单 `Step` 循环 → 席位调度器（含各席位独立期限与超时提交 `wait`）。
- `ObserverProjection` 硬编码实体 `player`/`key`/`core`/`door`/`exit`，且一次只产出一份 patch；N 个席位可见性不同 → 每视图一份 patch（扇出成本与记录体积需评估）。
- `RunCommitter` 的提交顺序不变，但每步要记录 seat 与"是否因超时提交"。

**Cli**
- `run`/`play` 是单席位入口；需要会话入口（清单文件）、`--view spectator`、以及把人类席位与 Agent 席位混排。

**现有检查会失效或需改写**（改规则版本时不可避免，需明确迁移而非静默放宽）
- 断言实体 `key`/`door`/`player` 单实例的 Observer 检查、`LastSeq=26`/`envelopes=27` 这类固定序号的回放检查、以及冻结的单机成功哈希（`M6GoldenChecks`、Core 的 golden 向量）。做法：**保留 v1 检查与向量**，为 v2 增加独立检查与新的 golden 向量，而不是改旧值让测试变绿。

## 5. 验收计划（新增检查，M7 阶段）

1. **座次轮转确定性**：同一场景 + 同一按席位动作序列，两次运行（跨进程）得到相同逐步哈希与事件序列。
2. **哈希覆盖完整性**：只改变"非当前行动席位"的位置/库存，也必须改变哈希（防止漏编码某个席位）。
3. **信息隔离**：席位 A 的观测绝不包含只有席位 B 能看到的格；`verify` 能检出被篡改的他人视野数据。
4. **超时不留白**：静默席位产生**已提交的 `wait`**，记录仍可 `verify`，且不会无限阻塞其他席位。
5. **混合席位**：1 个人类（脚本化 stdin）+ 1 个进程 Agent 完成一局，`replay` 可离线播放、`verify` 通过。
6. **多视图 Observer**：每个视图 `base_seq` 连续、互不干扰；一个视图慢读只让自己脱离。
7. **进程清理**：N 个 Agent 进程在超时/取消时**整棵树**被清理（沿用 M6 的 pidfile+孙进程手法）。
8. **旧档案回归**：`facility-zero/1` 的单机档案仍能 `verify`（D10）。

## 7. 风险

- **墙钟污染确定性**（最高风险）：一旦"谁先动"依赖到达时间，跨进程哈希与 `verify` 全部失效。缓解：顺序只由座次决定；超时只影响"该席位本回合提交 `wait`"，且该结果写入记录。
- **每视图补丁扇出**：N 个视角 = N 份 patch，记录体积与发布成本线性增长，容易打满订阅队列造成 resync 风暴。缓解：先量测 2 席位的记录体积与发布耗时，再决定是否需要视图共享/差分压缩。
- **协议矩阵错配**：Agent/Observer/回放/场景任一停留在 v1 会造成"能记录不能核验"。缓解：D9 一次性冻结成套版本，并在 `verify` 明确报出版本不支持（沿用现有 `unsupported_version`）。
- **规则版本分叉**：保留 v1 会让 Core 同时存在两套规则。缓解：v1 只读冻结、不再演进；新特性只进 v2。
- **协作模式下的"搭便车"**：不影响首切片机制正确性，但会影响将来评测口径；先用每席位统计（回合数/动作数）记录，评测方案另立。

## 8. 尚未确定的问题（后续阶段）

1. **敌对模式的规则细节**：玩家之间如何互相干扰（阻挡、抢夺门卡、破坏门）？独立目标与成绩判定怎么算？——按 D12/D13 作为 `adversarial` 规则版本单独设计，需要时再研究。
2. **席位扩展**：3–4 席时的每视图补丁扇出与记录体积是否需要压缩或视图共享。
3. **网络接入**：本地版本落地后再评估 socket 传输、认证与远程超时策略（席位身份已与传输解耦，预期不重写协议）。
